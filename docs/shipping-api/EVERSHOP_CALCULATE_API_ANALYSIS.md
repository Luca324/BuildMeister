# Анализ встроенного механизма «API calculate» для расчёта доставки в EverShop

Документ описывает малоизвестный и не описанный в официальной документации EverShop механизм расчёта стоимости доставки через внешний API («API calculate»). Цель — закрыть пробел в документации и пояснить, когда этот механизм применим, а когда (как в случае интеграции с Bring и многими другими сервисами доставки) потребуется собственная реализация.

---

## 1. Где встречается эта возможность

### 1.1 Админка

В настройках доставки EverShop при редактировании **метода доставки для зоны** (Shipping Zone → метод) в блоке «Setup shipping cost» доступны четыре типа расчёта:

- **Flat rate** — фиксированная стоимость
- **Price based rate** — стоимость в зависимости от суммы заказа
- **Weight based rate** — стоимость в зависимости от веса
- **API calculate** — расчёт через API

При выборе **API calculate** появляется одно текстовое поле:

- **Placeholder:** «Calculate API endpoint»
- **Instruction (подсказка):** «This API will be called to calculate shipping cost. It supposed to return a number.»

Визуально это выглядит как «эндпоинт для расчёта», но по факту в это поле подставляется не URL и не путь, а **идентификатор маршрута (route id)** из роутера EverShop. Ни в интерфейсе, ни в официальной документации это не уточняется.

Компонент формы:  
`node_modules/@evershop/evershop/dist/components/admin/checkout/shippingSetting/MethodForm.js` (при выборе `calculation_type === 'api'` отображается поле `calculate_api`).

### 1.2 База данных

В таблице **`shipping_zone_method`** (связь «зона — метод доставки») есть колонка:

- **`calculate_api`** — `varchar`, по умолчанию `NULL`.

Ограничение в миграции:

- `cost IS NOT NULL OR calculate_api IS NOT NULL` — т.е. для метода в зоне должна быть либо фиксированная стоимость (`cost`), либо указан `calculate_api`.

Миграция: `node_modules/@evershop/evershop/dist/modules/checkout/migration/Version-1.0.1.js`.

### 1.3 Валидация при сохранении

При сохранении метода зоны с типом расчёта «api» проверяется наличие `calculate_api`:

- Файл: `node_modules/@evershop/evershop/dist/modules/checkout/api/addShippingZoneMethod/validateMethod.js`
- Если `calculation_type === 'api'` и `calculate_api` пустой — возвращается ошибка: «API calculation type requires calculate_api».

## 2. Что на самом деле подставляется в поле «Calculate API endpoint»

Значение из поля **`calculate_api`** используется как **первый аргумент функции `buildUrl(routeId, params)`** из роутера EverShop. То есть это **идентификатор зарегистрированного в приложении маршрута**, а не полный URL и не относительный путь, заданный вручную.

Код построения URL (одинаковый в обоих местах использования):

```javascript
const port = normalizePort();
let api = `http://localhost:${port}`;
api += buildUrl(shippingMethod.calculate_api, {
  cart_id: cart_id_or_cart_uuid,
  method_id: shippingMethod.uuid
});
// GET-запрос на api
```

Функция `buildUrl(routeId, params)` (файл `node_modules/@evershop/evershop/dist/lib/router/buildUrl.js`):

- Ищет в роутере маршрут с `id === routeId`
- Подставляет `params` в путь маршрута (path params или query — зависит от определения маршрута)
- Возвращает путь (без хоста), поэтому в коде к нему дописывают `http://localhost:${port}`

Итог: в поле «Calculate API endpoint» в админке нужно вводить **корректный route id** существующего маршрута приложения. Если такого маршрута нет, при вызове `buildUrl` будет выброшена ошибка («Route … is not existed» или «Could not build url for route …»).

## 3. Контракт API: запрос и ответ

Вызов всегда один и тот же: **GET-запрос** по сформированному URL. Параметры передаются через `buildUrl`, то есть вид URL зависит от того, как маршрут объявлен (например, `/api/carts/:cart_id/shipping-cost/:method_id` или с query-параметрами).

Фактически вызывающему коду нужны:

- **Параметры:** `cart_id` (uuid корзины), `method_id` (uuid записи из таблицы `shipping_method`).

Ожидаемый формат ответа:

- **Успех (HTTP 2xx):** тело ответа в формате JSON:
  ```json
  {
    "data": {
      "cost": <число>
    }
  }
  ```
  Стоимость доставки — одно число. Других полей контракт не описывает.

- **Ошибка (HTTP ≥ 400):** в одном месте кода при ошибке используется `response.data.message`, в другом — просто считается, что расчёт не удался. Для расчёта в корзине при ошибке в `shipping_fee_excl_tax` может быть установлена ошибка через `this.setError('shipping_fee_excl_tax', response.data.message)` и возвращается 0.

Итого: **один запрос по одной паре (cart_id, method_id) → одна стоимость (число)**. Ни списка вариантов, ни дополнительных метаданных (название тарифа, срок доставки, код продукта перевозчика и т.п.) контракт не предусматривает.

## 4. Где в коде используется calculate_api

### 4.1 Получение списка методов доставки для чекаута

**Файл:** `node_modules/@evershop/evershop/dist/modules/checkout/api/getShippingMethods/sendMethods.js`

Сценарий: запрос списка доступных методов доставки для корзины (по `cart_id`, `country`, опционально `province`). Для каждой записи из `shipping_method`, привязанной к зоне и удовлетворяющей условиям (цена/вес), проверяется способ расчёта:

- Если у метода в `shipping_zone_method` задан `calculate_api`, выполняется GET по URL, собранному из `buildUrl(method.calculate_api, { cart_id, method_id: method.uuid })`.
- В ответе ожидается `data.cost`. Это значение подставляется в объект метода и возвращается клиенту в списке методов (вместе с `id`, `code`, `name`, `cost`).

Таким образом, на фронте чекаута пользователь видит список методов с уже посчитанной стоимостью; для методов с «API calculate» эта стоимость приходит с вашего эндпоинта.

### 4.2 Расчёт стоимости выбранного метода в корзине

**Файл:** `node_modules/@evershop/evershop/dist/modules/checkout/services/cart/registerCartBaseFields.js`

Резолвер поля **`shipping_fee_draft`** корзины вычисляет стоимость доставки для уже выбранного метода:

1. Загружается запись метода из БД (по `shipping_method` в корзине — это uuid метода из таблицы `shipping_method`).
2. Если у метода задан `cost` (фиксированная ставка) — используется он.
3. Иначе если задан `calculate_api` — выполняется GET с `cart_id` (uuid корзины) и `method_id` (uuid метода). Из ответа берётся `response.data.data.cost` и возвращается как стоимость доставки.
4. Иначе используются `weight_based_cost` или `price_based_cost`, если заданы.
5. Если ничего не подошло — устанавливается ошибка «Could not calculate shipping fee» и возвращается 0.

Важно: в корзине в `shipping_method` хранится **только uuid одной записи** из `shipping_method`. Никакого дополнительного «выбранного варианта» (например, конкретного тарифа Bring) ядро не хранит и не передаёт в этот запрос.

---

## 5. Почему в документации об этом нет

В официальной документации EverShop механизм «API calculate» и поле `calculate_api` не описаны. Поведение восстанавливается только по коду:

- админка: `MethodForm.js`;
- валидация: `validateMethod.js`;
- использование: `sendMethods.js`, `registerCartBaseFields.js`;
- роутер: `buildUrl.js`;
- схема БД: миграции checkout.

Удобно ориентироваться по пакету `@evershop/evershop` в `node_modules` и путям выше.

## 6. Ограничения модели «один метод — одна цена»

Из контракта и кода следуют такие ограничения:

1. **Один метод доставки в БД = один «тип» с одной ценой за запрос.**  
   Нет контракта «вернуть несколько вариантов с разными названиями и ценами». Есть только «для этого method_id верни одно число cost».

2. **В заказе сохраняется только идентификатор метода.**  
   В корзине и заказе в поле `shipping_method` попадает uuid записи из `shipping_method`. Нет отдельного поля для «варианта» (код продукта перевозчика, deliveryOptionId, тариф и т.д.). Поэтому после оплаты создать отправление в стороннем API можно только если по этому uuid вы можете однозначно восстановить, что именно выбрал пользователь. При нескольких тарифах у одного перевозчика так сделать нельзя без расширения модели (доп. поле или свой формат хранения).

3. **Адрес и состав корзины в контракт не передаются явно.**  
   В вызов вашего маршрута передаются только `cart_id` и `method_id`. Чтобы учитывать адрес доставки или товары, ваш эндпоинт должен сам загрузить корзину по `cart_id` и при необходимости адрес из связанных таблиц. Стандартного параметра «адрес» или «список товаров» в контракте нет.

4. **Только GET и только один ответ — число.**  
   Нет сценария «создать отправление» или «забронировать слот» в рамках этого механизма. Расчёт стоимости — единственная предусмотренная операция.

## 7. Почему это не подходит для Bring и для большинства сервисов доставки

### 7.1 Bring как типичный пример

Сервис Bring (и многие другие перевозчики) работают по модели:

- **Расчёт:** по адресу, весу, габаритам возвращается **список вариантов** (например, «Pakke til hentested», «Pakke hjem», «Pakke til bedrift» и т.д.) с разными ценами и сроками.
- **Выбор:** пользователь выбирает **один вариант** из списка.
- **Создание отправления:** после оплаты магазин вызывает Booking API перевозчика, передавая **именно выбранный вариант** (product id / deliveryOptionId и т.п.), и получает трекинг, этикетки, QR и т.д.

Модель EverShop «API calculate» предполагает:

- Один метод в БД → один запрос → одна цена.
- В заказе хранится только uuid метода, без «варианта».

Поэтому:

- Нельзя «честно» отдать в одном методе несколько вариантов Bring с разными ценами: контракт даёт одну цену на один `method_id`.
- Можно было бы завести в `shipping_method` отдельную запись на каждый вариант Bring (например, «Bring Pakke til hentested», «Bring Pakke hjem») и для каждой указать один и тот же `calculate_api`; тогда по `method_id` ваш эндпоинт мог бы возвращать разную цену. Но тогда:
  - список методов на чекауте будет жёстко задан в БД, а не приходит динамически из API Bring по адресу;
  - после оплаты в заказе будет только uuid такой записи — для вызова Booking API вам всё равно нужно где-то хранить «какой именно продукт Bring выбран» (deliveryOptionId и т.д.). Ядро такого поля не предоставляет.
- Итог: без расширения модели (отдельное поле под метаданные выбранного варианта или свой формат в `shipping_method`) полноценная интеграция Bring через один только «API calculate» невозможна.

В данном проекте интеграция Bring реализована иначе: отдельный блок на чекауте, GraphQL-мутация для расчёта вариантов, сохранение выбранного варианта (в т.ч. для создания отправления после оплаты). Подробнее см. раздел 9 и ссылки на код репозитория ниже.

### 7.2 Обобщение на другие сервисы доставки

Большинство современных сервисов доставки (перевозчики, агрегаторы) предоставляют:

- **Варианты доставки** (несколько тарифов/способов с разными ценами и сроками).
- **Выбор одного варианта** пользователем.
- **Booking/Shipment API** после оплаты с передачей выбранного варианта (product id, service code и т.п.).

Модель EverShop «API calculate» не рассчитана на «несколько вариантов» и на сохранение «выбранного варианта» для последующего букинга. Поэтому она плохо подходит не только для Bring, но и для большинства подобных интеграций без доработки (доп. поля, свой UI и поток).

Исключением могли бы быть сервисы, которые по сути дают **одну цену на направление** (например, один тариф «доставка в страну X» без выбора конкретного продукта/тарифа) и не требуют передачи «варианта» при создании отправления. Тогда один метод в БД = один такой сервис, `calculate_api` возвращает одну цену по `cart_id`/`method_id`, а создание отправления (если оно вообще есть у перевозчика) могло бы делаться по другим правилам (например, по умолчанию один продукт). Такие случаи редки; обычно у перевозчика есть несколько продуктов/тарифов.

## 8. Можно ли «вписаться» в контракт EverShop со стороны перевозчика

Теоретически — да, но только в узком случае:

- У перевозчика есть API «по корзине/адресу верни одну стоимость» (без выбора варианта).
- После оплаты создание отправления либо не требуется, либо делается без указания «варианта» (один тип отправления по умолчанию).

Тогда вы:

- Регистрируете в приложении маршрут с фиксированным route id (например, `getShippingCostCarrierX`).
- В админке для метода «Carrier X» указываете `calculate_api` = этот route id.
- В обработчике маршрута по `cart_id` загружаете корзину и адрес, вызываете API перевозчика, получаете одну цену и возвращаете `{ data: { cost: number } }`.

Для Bring и аналогов это не подходит: у них несколько продуктов/тарифов и обязательный выбор варианта для букинга.

## 9. Как в данном проекте решена интеграция с Bring (без опоры на calculate_api)

В этом репозитории интеграция с Bring сделана **минуя** встроенный «API calculate»:

- **Расчёт вариантов:** отдельный компонент на чекауте запрашивает варианты через GraphQL-мутацию `calculateShipping`, бэкенд вызывает Shipping Guide API Bring и возвращает список вариантов с ценами и сроками. Один общий список методов EverShop при этом не подмешивается; варианты Bring показываются в своём блоке (см. план в `docs/shipping-api/PLAN_BRING_IMPLEMENTATION.md`).
- **Сохранение выбора:** при переходе к оплате вызывается мутация `updateCartShippingMethod`, в корзину сохраняется полный объект метода (в т.ч. `provider`, `metadata.deliveryOptionId` и т.д.). Из-за того что ядро ожидает в `shipping_method` uuid из таблицы `shipping_method`, при создании заказа возникает ошибка валидации «Shipping method is required» — это обходится либо патчем резолвера корзины, либо (рекомендуемый вариант) введением отдельного поля `shipping_method_metadata` и хранением в `shipping_method` uuid одного «фиктивного» метода Bring, а в метаданных — полного JSON для букинга (см. обсуждение в плане и в коде расширения).
- **Создание отправления:** после оплаты процессор `ShippingOrderProcessor` (событие `orderCreateAfter`) читает из заказа данные метода доставки (в т.ч. `provider`, `metadata.deliveryOptionId`), вызывает Bring Booking API и создаёт запись в таблице `shipment`.

Ключевые файлы в репозитории:

- Расширение доставки: `extensions/shipping-api/`
- Резолверы мутаций (расчёт и сохранение метода): `extensions/shipping-api/src/graphql/types/ShippingMutation/ShippingMutation.resolvers.ts`
- Компонент выбора вариантов на чекауте: `extensions/shipping-api/src/pages/frontStore/checkout/ShippingOptionsBlock.tsx`
- Процессор создания отправления: `extensions/shipping-api/src/services/ShippingOrderProcessor.ts`
- План реализации Bring: `docs/shipping-api/PLAN_BRING_IMPLEMENTATION.md`
- Документация по API Bring: `docs/shipping-api/bring_api.md`, `docs/shipping-api/bring_booking_api.md`, `docs/shipping-api/bring_shippingguide_api.md`

Такой подход даёт полный контроль над списком вариантов, выбором пользователя и созданием отправления и не упирается в ограничения «один method_id — одна цена» и отсутствие поля для «варианта» в ядре EverShop.

---

## 10. Краткие выводы для разработчиков на EverShop

1. **«Calculate API endpoint» в админке** — это **route id** маршрута вашего приложения, а не URL. Маршрут должен принимать `cart_id` и `method_id` и возвращать JSON `{ data: { cost: number } }`.

2. **Контракт жёсткий:** один запрос → одна стоимость. Список вариантов доставки с разными ценами и сохранение «выбранного варианта» для букинга этим механизмом не предусмотрены.

3. **Для интеграций вроде Bring и большинства перевозчиков** встроенного «API calculate» недостаточно; нужна своя схема: отдельный UI, свой формат хранения выбранного варианта (и при необходимости — отдельное поле метаданных), процессор после оплаты для вызова Booking/Shipment API.

4. **Документации по «API calculate» в EverShop нет** — поведение можно восстановить только по коду пакета `@evershop/evershop` (пути к файлам приведены выше). Данный документ и ссылки на код репозитория могут служить отправной точкой для главы статьи, закрывающей этот пробел в документации.
