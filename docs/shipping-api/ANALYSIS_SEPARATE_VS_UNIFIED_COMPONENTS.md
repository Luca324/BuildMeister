# Анализ: Раздельные компоненты vs Объединенный компонент для выбора доставки

## Контекст проблемы

В расширении `shipping-api` реализованы два подхода к отображению вариантов доставки:

1. **Процессор `ShippingCalculationProcessor`** - пытается добавить динамические варианты от API провайдеров в стандартный список методов EverShop через процессор `cartCalculateShipping`
2. **Отдельный компонент `ShippingOptionsBlock`** - отображает варианты от API провайдеров в отдельном блоке

При попытке объединить их в один компонент возникли сложности с перехватом событий и встраиванием данных от API в нативный компонент EverShop.

---

## Различия в логике обработки

### Нативные методы доставки (EverShop)

**Источник данных:**
- Таблица `shipping_zone_method` в БД
- Добавляются администратором через админ-панель
- Статические методы с фиксированной стоимостью

**Логика обработки:**
1. Пользователь выбирает метод из списка
2. Метод сохраняется в `cart.shipping_method` (ID метода)
3. Стоимость доставки добавляется к итоговой сумме заказа
4. При создании заказа метод копируется в `order.shipping_method`
5. **Никаких дополнительных действий не требуется**

**Формат данных:**
```typescript
{
  method_id: "123",  // ID из shipping_zone_method
  name: "Стандартная доставка",
  cost: 199
}
```

### API методы доставки (Bring, PostNord, Helthjem)

**Источник данных:**
- API провайдеров доставки (динамический расчет)
- Зависят от адреса получателя, веса, габаритов
- Могут быть недоступны для некоторых адресов

**Логика обработки:**
1. Пользователь выбирает вариант из списка
2. Метод сохраняется в `cart.shipping_method` с метаданными (JSON):
   ```typescript
   {
     method_id: "api_bring_123",
     provider: "bring",
     price: 249,
     metadata: {
       deliveryOptionId: "123",
       serviceCode: "SERVICE_123",
       estimatedDays: 3
     }
   }
   ```
3. Стоимость доставки добавляется к итоговой сумме заказа
4. При создании заказа метод копируется в `order.shipping_method`
5. **После успешной оплаты:**
   - Вызывается `ShippingOrderProcessor`
   - Создается отправление через API провайдера (`createBooking()`)
   - Получается `trackingNumber` и QR код
   - Сохраняется в таблицу `shipment`
   - Отправляется email продавцу с QR кодом

**Формат данных:**
```typescript
{
  method_id: "api_bring_123",
  provider: "bring",
  price: 249,
  metadata: {
    deliveryOptionId: "123",
    serviceCode: "SERVICE_123",
    estimatedDays: 3
  }
}
```

## Анализ подхода 1: Объединение через процессор

### Как это работает

Процессор `ShippingCalculationProcessor` добавляет динамические методы в массив методов доставки через процессор `cartCalculateShipping`:

```typescript
addProcessor('cartCalculateShipping', async (cart, methods, context) => {
  // Получаем варианты от API провайдеров
  const dynamicMethods = await getApiMethods(cart);
  // Добавляем к стандартным методам
  return [...methods, ...dynamicMethods];
});
```

### Проблемы этого подхода

#### 1. **Разный формат данных**

Нативные методы имеют структуру:
```typescript
{
  id: "123",
  method_id: "123",
  name: "Стандартная доставка",
  cost: 199
}
```

API методы имеют дополнительную структуру:
```typescript
{
  id: "api_bring_123",
  method_id: "api_bring_123",
  name: "Bring Standard",
  cost: 249,
  provider: "bring",
  metadata: { ... }
}
```

**Проблема:** Нативный компонент EverShop может не ожидать поля `provider` и `metadata`, что может привести к ошибкам при рендеринге или обработке.

#### 2. **Разная логика обработки выбора**

**Нативные методы:**
- Выбор обрабатывается стандартным компонентом EverShop
- Сохраняется только `method_id`
- Никаких дополнительных действий

**API методы:**
- Требуют сохранения метаданных (provider, deliveryOptionId)
- После оплаты требуют создания отправления через API
- Требуют обработки ошибок API

**Проблема:** Нужно перехватывать событие выбора метода и определять, какой тип метода выбран, чтобы применить правильную логику обработки.

#### 3. **Сложность перехвата событий**

Нативный компонент EverShop использует внутренние обработчики событий, которые:
- Могут быть не документированы
- Могут изменяться при обновлениях EverShop
- Могут быть недоступны для перехвата из расширения

**Проблема:** Непонятно, какое событие перехватывать и как встроить логику обработки API методов.

#### 4. **Встраивание данных от API**

Данные от API провайдеров:
- Загружаются асинхронно (debounce при изменении адреса)
- Могут быть недоступны (ошибки API)
- Могут изменяться при изменении адреса

**Проблема:** Нужно синхронизировать асинхронные данные от API с синхронным рендерингом нативного компонента, что создает сложности с состоянием и обновлением UI.

#### 5. **Обработка ошибок**

При ошибках API:
- Нужно показывать сообщения об ошибках
- Нужно обрабатывать недоступность провайдеров
- Нужно не блокировать выбор нативных методов

**Проблема:** Нативный компонент может не поддерживать отображение ошибок для отдельных методов, что требует дополнительной логики.

## Анализ подхода 2: Раздельные компоненты

### Как это работает

1. **Нативный компонент EverShop** отображает статические методы доставки
2. **Компонент `ShippingOptionsBlock`** отображает варианты от API провайдеров
3. Оба компонента используют radiobutton с одним `name`, что обеспечивает единый выбор

### Преимущества этого подхода

#### 1. **Разделение ответственности**

- Нативный компонент обрабатывает только статические методы
- API компонент обрабатывает только динамические методы
- Каждый компонент имеет свою четко определенную область ответственности

#### 2. **Простота реализации**

- Не нужно перехватывать события нативного компонента
- Не нужно встраивать данные в нативный компонент
- Каждый компонент работает независимо

#### 3. **Гибкость обработки**

- API компонент может иметь свою логику debounce
- API компонент может обрабатывать ошибки независимо
- API компонент может обновляться при изменении адреса без влияния на нативный компонент

#### 4. **Изоляция ошибок**

- Ошибки API не влияют на отображение нативных методов
- Можно показывать ошибки для каждого провайдера отдельно
- Нативные методы остаются доступными даже при недоступности API

#### 5. **Простота поддержки**

- Код разделен на логические части
- Легче тестировать каждый компонент отдельно
- Легче добавлять новых провайдеров без изменения нативного компонента

### Недостатки этого подхода

#### 1. **Визуальное разделение**

- Два списка вариантов могут выглядеть как два независимых выбора
- Пользователь может подумать, что можно выбрать по одному варианту из каждого списка

**Решение:** Использовать один `name` для всех radiobutton, что обеспечивает единый выбор на уровне HTML.

#### 2. **Дублирование логики**

- Оба компонента отображают radiobutton
- Оба компонента обрабатывают выбор метода

**Решение:** Это минимальное дублирование, которое оправдано разделением ответственности.

## Сравнение сложности реализации

### Объединенный подход

**Сложность:** ⭐⭐⭐⭐⭐ (Очень высокая)

**Требуется:**
1. Изучить внутреннюю структуру нативного компонента EverShop
2. Найти способ перехвата событий выбора метода
3. Встроить асинхронные данные от API в синхронный рендеринг
4. Обработать разные форматы данных (нативные vs API)
5. Реализовать условную логику обработки в зависимости от типа метода
6. Обработать ошибки API без влияния на нативные методы
7. Синхронизировать состояние при изменении адреса

**Риски:**
- Код может сломаться при обновлении EverShop
- Сложность отладки из-за переплетения логики
- Сложность поддержки и расширения

### Раздельный подход

**Сложность:** ⭐⭐ (Низкая)

**Требуется:**
1. Создать отдельный компонент для API методов
2. Использовать один `name` для всех radiobutton
3. Реализовать свою логику debounce и обработки ошибок
4. Сохранять выбранный метод через GraphQL mutation

**Риски:**
- Минимальные, так как компоненты изолированы

## Выводы и рекомендации

### Вывод 1: Раздельный подход проще и надежнее

Раздельные компоненты имеют **значительно меньшую сложность** реализации и поддержки. Объединение требует глубокого понимания внутренней структуры EverShop и создает множество точек отказа.

### Вывод 2: Визуальное единство можно обеспечить

Проблема "двух списков" решается использованием одного `name` для всех radiobutton. Это стандартный HTML подход, который гарантирует единый выбор.

### Вывод 3: Разделение ответственности - правильный подход

Нативные методы и API методы имеют **принципиально разную логику обработки**:
- Нативные: просто увеличивают стоимость
- API: требуют создания отправления после оплаты

Разделение компонентов соответствует принципу разделения ответственности (Separation of Concerns).

### Вывод 4: Объединение создает технический долг

Попытка объединить компоненты создает:
- Сложный код, зависящий от внутренней структуры EverShop
- Точки отказа при обновлениях EverShop
- Сложность отладки и поддержки

### Рекомендация: Использовать раздельный подход

**Рекомендуется оставить раздельные компоненты** по следующим причинам:

1. **Простота реализации** - код понятен и легко поддерживается
2. **Надежность** - компоненты изолированы, ошибки не распространяются
3. **Гибкость** - легко добавлять новых провайдеров
4. **Соответствие принципам** - разделение ответственности

**Улучшения для раздельного подхода:**

1. **Визуальное единство:**
   - Использовать один `name="shipping-method"` для всех radiobutton
   - Стилизовать оба компонента в едином стиле
   - Добавить визуальное разделение (например, разделитель) только если нужно показать группировку

2. **Улучшение UX:**
   - Показывать оба списка рядом или последовательно
   - Добавить заголовок "Доставка через API провайдеров" для ясности
   - Обеспечить, чтобы выбор в одном списке снимал выбор в другом

3. **Обработка выбора:**
   - Унифицировать сохранение метода через один GraphQL mutation
   - Обрабатывать оба типа методов в одном месте (ShippingOrderProcessor уже это делает)

---

## Заключение

**Объединение компонентов создает больше проблем, чем решает:**

- Требует глубокого понимания внутренней структуры EverShop
- Создает сложный код с множеством точек отказа
- Усложняет поддержку и расширение
- Не дает значительных преимуществ в UX

**Раздельный подход является правильным решением:**

- Простой и понятный код
- Изолированные компоненты
- Легкая поддержка и расширение
- Соответствие принципам разработки

**Рекомендация:** Оставить раздельные компоненты и улучшить их визуальное единство через стилизацию и использование одного `name` для radiobutton.
